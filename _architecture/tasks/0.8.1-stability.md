# 0.8.1 stability task spec

Status: research draft; implementation has not started.
Baseline: `8b171ef` (`0.8.0`). Research date: 2026-10-24.

Objective: fix reproducible stalls, event loss, and incorrect retry behavior
without expanding the public command, SDK, configuration, or wire surfaces.

## Proposed release scope

| Task | Priority | Observed failure | Size estimate |
| --- | --- | --- | --- |
| STAB-01 | P1 | A filtered prefix permanently stalls file log shipping | Small |
| STAB-02 | P1 | A late log ACK applies an old offset to a replacement file | Medium |
| STAB-03 | P1 | Settling a spool segment deletes a newer file at the same name | Medium |
| STAB-04 | P2 | A retry begins after its declared window has expired | Small |
| STAB-05 | P2 | Reconnect reverses the order of unacknowledged event batches | Small |

All five failures were reproduced locally against the baseline. Priorities
reflect impact, not evidence of a production incident. Sizes are estimates,
not implementation commitments. Implement STAB-01 and STAB-02 together because
both affect log cursor ownership; the remaining tasks can be delivered separately.

## STAB-01: allow filtered log ranges to make progress

Locations: `stormpulse/logging/shipper.py:75`,
`stormpulse/logging/tailer.py:43`, `stormpulse/agent/loops.py:115`.

`collect_batch()` returns `None` when every line in a read fails
`filter_contains`. The file tailer reads from the last confirmed position,
and this path produces neither a batch nor a position confirmation.

Reproduction: write three valid log lines, with messages `skip1`, `skip2`,
`needle`. Set the filter to `needle` and the batch limit to two. Three successive
collections return `None`; the persisted position stays `(0, None)`. The third
line is never reached even though it matches the filter.

Required outcome: intentional exclusions consume their source range so later
matching records can be shipped. Preserve the delivery guarantee for records
that do match. Choose a local checkpoint or an existing empty-batch/ACK path
after checking its interaction with outstanding batches; no new wire message.

Acceptance criteria:

- The reproduction reaches and ships `needle` within a bounded number of reads.
- A wholly excluded read makes progress without counting excluded lines as
  parser failures.
- When a read includes matching records, failure to send or receive an ACK
  cannot checkpoint past those records.
- Restart, delayed ACK, and rotation cases preserve those properties.
- Check the corresponding filtering paths for Docker and journald, including
  streaming Docker replay after reconnect; do not assume identical cursor behavior.

## STAB-02: associate each log ACK with its original source generation

Locations: `stormpulse/logging/tailer.py:43`,
`stormpulse/logging/tailer.py:104`, `stormpulse/agent/log_batches.py`,
`stormpulse/agent/acks.py:55`, `stormpulse/logging/positions.py`.

The pending receipt retains only a group and target position. A file tailer's
`_pending_inode` belongs to its latest read, not to the batch being acknowledged.
`confirm_shipped(old_offset)` can therefore store that offset against a new inode.

Reproduction: read an old file whose first range ends at byte 26. Rotate it by
rename and create a replacement. Read the replacement, then append more lines.
Confirm the old range at byte 26. The database stores `(26, new_inode)` and the
next read returns only `hird\n`, starting in the middle of the replacement's
third line. Earlier replacement records have been skipped.

Required outcome: keep immutable, local source identity with every receipt and
apply confirmations only to the generation and range they actually cover.
Scope receipt metadata internally so the wire contract remains unchanged.

Acceptance criteria:

- A late old-file ACK cannot advance the replacement file's checkpoint.
- ACKs arriving out of order for the same generation cannot rewind a confirmed
  checkpoint or skip an unconfirmed gap.
- Test multiple reads and ACKs around rename rotation, truncation in place,
  and reconnect. Define truncation handling explicitly; inode alone is insufficient.
- Unknown, duplicate, and expired receipts cannot change a checkpoint.
- Audit timestamp and opaque journald cursor confirmations for the equivalent
  stale-ACK problem; do not impose numeric ordering on opaque cursors.
- Reproduce using real files and SQLite, without faking host identity.

## STAB-03: settle the spool file that was read

Locations: `stormpulse/agent/event_spool.py:141`,
`stormpulse/agent/event_spool.py:213`, `stormpulse/bounded_read.py`.

`_pending` tracks segment names and event sequence ranges. Once the range is
settled, `_settle(name)` unlinks whatever currently occupies that pathname.
The published segment format does not require names to remain unique forever.

Reproduction: ingest record `old` from `0001.jsonl`. Atomically replace that
path with a segment carrying record `replacement`. ACK the old batch and tick
the feeder. The replacement file is deleted, and no replacement record is
buffered or shipped.

Required outcome: preserve the identity of the segment actually ingested and
prevent its settlement from deleting a replacement. Account for replacement
between checking identity and unlinking, rather than relying on an unchecked
pathname. Preserve retry behavior when a settled file cannot be deleted.

Acceptance criteria:

- In the reproduction, `replacement` remains available and is eventually shipped.
- Replace a file while its events span multiple batches; settling one or all
  old batches must never settle the replacement's events.
- Exercise ACK, NACK, buffer eviction, missing files, and failed deletion.
- Preserve the existing reconnect behavior and documented restart deduplication
  responsibility. This task does not promise exactly-once delivery.
- Test replacement races with real atomic renames and synchronization gates.

## STAB-04: check the retry deadline when an attempt can actually start

Locations: `stormpulse/commands/jobs.py:175`,
`stormpulse/commands/jobs.py:453`,
`_architecture/adrs/core/012-a-job-may-ask-to-run-again.md`.

The deadline is checked before parking. After sleep and semaphore reacquisition,
the next handler runs without checking whether the window is still open.

Reproduction: use a single execution permit, a two-second retry window, and a
first outcome asking for a one-second delay. Let another job occupy the permit
for 2.2 seconds. The second attempt starts at approximately `+2.2s`, succeeds,
and reports `attempts=2`, `retries_exhausted=false`.

Required outcome: once opened by the first execution permit, the retry window
also bounds admission to later attempts. If the window closes while parked or
waiting for a permit, finalize the last actual outcome as exhausted. An already
running attempt may complete; this is not a new execution timeout.

Acceptance criteria:

- Cover semaphore contention and an overslept retry delay deterministically.
- No later handler invocation begins at or beyond the chosen expiry boundary;
  document and test the exact-boundary rule.
- `attempts` counts handler invocations, not proposed or abandoned attempts.
- Exhaustion preserves the last outcome, structured error, and work duration;
  parked and queued time stays excluded from work duration.
- Time before the first permit still spends none of the window. Parking still
  releases the permit. Shutdown still produces no contradictory terminal result.

## STAB-05: preserve batch order when reconnect requeues events

Location: `stormpulse/events.py:342`.

`requeue_unacked()` visits batches in insertion order but prepends each batch
to the queue. That preserves order within a batch and reverses order between
batches, contradicting its own oldest-first guarantee.

Reproduction: buffer records `1,2,3,4`; drain two batches of two; requeue and
drain again. The output is `3,4,1,2`.

Required outcome: restore unacknowledged batches in original send order ahead
of records that were never sent, while retaining existing sequence numbers.

Acceptance criteria:

- Requeue at least three differently sized batches plus unsent records and
  verify their complete order.
- ACK a middle batch before reconnect and verify the surviving order.
- When requeue exceeds capacity, drop the oldest records in the correctly
  reconstructed stream and report the exact loss count.
- Repeated reconnects neither duplicate buffered records nor restamp their seqs.
- Keep the existing drop-summary behavior; do not redefine all event sequence
  semantics as part of this fix.

## Investigation candidates outside the committed scope

These are code-backed concerns, not reproduced product defects in this pass.
Promote one only after adding a focused reproduction and acceptance criteria.

1. **Worker ownership across reconnect.** Per-session loops await
   `asyncio.to_thread()`, while feeders, tailers, and some readers survive the
   session. Cancelling an await does not stop a worker that is already running
   ([Python executor documentation](https://docs.python.org/3.12/library/concurrent.futures.html#concurrent.futures.Future.cancel)).
   Inspect `stormpulse/agent/reconnect.py:159` and
   `stormpulse/agent/loops.py:191` for overlapping spool ticks and tailer drains
   after a quick reconnect. Garage already serializes full collection with
   `_collect_lock`; a blanket claim that all collectors race would be wrong.
   First task: gate a real feeder read, end its session, start another session,
   and verify whether the same segment is admitted concurrently. The exploratory
   overlap probe did not complete, so no overlap result is claimed here.
2. **ACK delays behind inline commands.** `receive_loop()` awaits each dispatch.
   Refresh, subprocess commands, and sequences can occupy the inbound dispatcher
   while telemetry ACKs wait. Investigate this against the 30-second pending-log
   receipt timeout and bounded event batches. Any fix must bound admission and
   retain job ownership and sequence ordering; avoid unbounded task spawning.
3. **Raw log input bounds.** File reads use unbounded `readline()`, and streaming
   Docker accumulates data until newline. Measure behavior with a very long line
   and a stream without newline before proposing byte budgets and recovery rules.

The release-update policy in CORE-002 is another existing stability direction:
plain update still selects `main`. Its documented release-tag selection and
build provenance work is explicitly marked unbuilt. Keep that separate: it
changes operator-visible behavior and should be scoped against CORE-002's
minor-versus-patch rule before including it in a release named `0.8.1`.

## Verification and completion

Research performed with Python 3.12.13. The five reproductions used local files,
SQLite, the real spool feeder and event buffer, and the actual job runner.
The contention reproduction used a real semaphore and elapsed time; implementation
tests should replace timing guesses with controlled synchronization and a clock.

Existing focused tests: **61 passed** using:

```sh
.venv/bin/python -m pytest -q tests/logging/test_shipper.py tests/logging/test_tailer.py tests/test_events.py
```

The full default suite and a broader focused selection were interrupted after
they stopped producing progress; neither has a completed result. The cause was
not established. Wire tests, CI-container tests, type checking, security scans,
and the full release gates were not completed in this research pass.

Implementation completion requires:

- A failing regression for each selected defect, then the fix and a passing test.
- All selected acceptance criteria, including cross-task cursor interactions.
- `make check` and `make test-ci`; run Garage wire tests if Garage code changes.
- Generated contract comparison: unchanged public shapes, digests, and SDK API.
- A patch-only changelog entry describing the actual fixes. Stop and rescope
  if a solution needs Added, Changed, or Removed behavior under CORE-002.
- At release preparation, matching version/changelog checks and wheel smoke
  verification from the committed release candidate. Publishing remains a
  separate maintainer action.
